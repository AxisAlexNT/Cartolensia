# Cartolensia
An open-source and free self-hosted multimedia service called "Cartolensia". The service would feature GPS track snapping, AI methods for sorting and uniting, AI methods for classifying places, landscapes, vehicles (like different models of buses, trains and possibly even reading their running numbers from photos), automatic transcoding engine for saving stuff in AV1 with minimum quality losses and like without loosing readability of texts. It is more tourist, railway-fan (or transport fan in general), biker/hiker-oriented. Not only to make "vivid memories", "family albums" and "nostalgic feelings" like most other competing software does, but to make large (multi-terabyte) multimedia collection (different years, different devices, different formats, etc) be quickly and easily searchable and addressable, easily manageable, with photos and GPS tracks on maps, time snapping, geotag prediction, etc. So like if you are asked about whether some other's photo rings a bell - you could upload and immediately find photos alike in your collection (not by fetching and comparing each, but by utilizing vector embeddings). If you are asked about some artifact during your 10-year-ago trip - it must be easily findable just by scrolling the map and easily pointing it out, without having to remember an exact year. Or even to just enter the text description, and a local LLM would try to select important features and keywords, encode in as a query and fast-fetch matching photos. The same would be great with videos (independent audio and video - in regular frame intervals - analysis). And the app itself is fast and portable (Go backend, Vue3+Typescript frontend), most of the features are modular like plugins, so development is easy and independent for different features, and the app is snappier. And yeah, AI plugins must support running PyTorch on all kinds of hardware (NVidia GPUs, AMD GPUs, Intel GPUs, CPUs of all sorts).

Probably it should be orchestrated as a multipart Docker Compose app, with multiple services, inter-service networking, host networking for exported services, and persistent storages.

Core of the app should mainly provide the essential tasks as the data and database management, replication, metadata backups, efficient fetching and storing, and translating different storage backends. The database must be PostgreSQL-powered for optimal resilience and performance. (Make a debugging scripts and configuration that creates like dev container with PostgreSQL for building/debugging/testing). Configuration must be done via YAML files: main directory YAML with general config like DB URL, enabled plugins, enabled storage backends and their configuration. For each plugin, its own configuration could be saved in the YAML file in its own plugin folder, in the same folder where plugin definition YAML resides, declaring like name, description and other plugin dependencies that are to be used in topological sorting for loading plugins in correct order to resolve dependencies. Both the main config file and plugins' configs are to be also backed up into PostgreSQL DB, so it captures the whole state of app at all times when cold. Plugins must also have  a way to communicate with DB, either via core's API like lists and mappings, or directly via another DB connection for custom operations. Storage backends must be adapters, the main key for each file should be its SHA512 sum (however, in case of collisions use special case to reference new SHA512 sums for that), and secondary keyset has to be URLs of each multimedia file. This way, moving indexed files into different subdirectories mustn't create new records, just update URL, since SHA512 sum won't change, storage must be resilient to file moving/regrouping into different folders. Core is also responsible for extracting, parsing and storing/serving all the metadata of photos, like when they are taken, where, all EXIF data, etc. Each adapter has to translate its backend storage do the universal URLs. Right now should be implemented generic FS storage adapter (which requires its storage root directory to be set, and it is treated like a regular file path on this machine), SMB storage adapter (read multimedia from smb:/// server), NFS server (the same for UNIX), and probably S3 storage adapter (universal for Amazon, MinIO, RustFS). In addition to backend-specific options, all storage adapters must have configurable read/write control, default set to "read-only" (so that the originals are never modified/deleted, these operations on adapter level become not implemented, however the metadata stored in app's database could be modified), and have three modes: strict read-only (default), journaled/deferred (allow modify/delete operations and make list of them, but not execute, then only after the user reviews the list in UI and confirms by entering something, operations are executed in backend storage), and full access (read+write without excessive confirmations, ask only when action is done, not after), also make configurable "Trash" folder to which move deleted/duplicate/etc files instead of real deletion. I want most of the functionality to be implemented as a plug-ins, so each plugin is put into `plugins/` folder and has `core/` and `webui/` subdirectories. App frontend should be configurably served on HTTP/HTTPS (or both), and in HTTPS case a certificate might be provided, or a strong self-signed certificate is to be issued, depending on configuration. Multiple storages could be selected, even with different backends, only requirement is different name, so URLs are different. One could be read-only (like originals on NAS mounted via SMB/NFS), other could be read+write (like "work" storage, where transcoded videos are to be stored before user explicitly confirms replacing original with transcoded version, in which case it's be copied over to originals when read-only is disabled, then checked, only then original video is trashed or deleted). Also core must be responsible for user/groups/authentication providers and access restrictions. By default admin user has all access to all multimedia (only respecting app-wide config, like admin still can't delete from read-only storage adapter, but can switch it to another mode in settings). Admin could create public album links and share to friends not requiring authentication, or requiring authentication, might create new users, might allow user registration and user data upload, etc. Indexing ("Originals discovery") should also have its own dedicated page and controller, and provide logs, current progress, best-effort ETA and other statistics, like number of photos scanned, number of new photos detected, number of duplicates detected, total amount of data scanned (like in GB) and total amount of new files (in GB), etc. Also should be admin-available statistics page and backend status pages, where technica details, server load, workers numbers, pools sizes, duplicates counts, number of hash collisions, etc be displayed.

Base plugins to be included are photo albums plugin, photos+videos+tracks on map plugin, GPS tracks manager plugin, video transcoding manager, base AI features manager, AI classification manager.

General view (embedded in core, not a plugin, always included in the base) is like a file explorer with the same folders as in the storage, and in table view with configurable columns (total columns set is the union of all columns extracted from the multimedia, like date, size, all EXIF fields) and each should allow sorting or filtering (like in Google Sheets). It should also allow uploading files via WebUI or WebDAV.

Photo albums should allow grouping photos/videos/GPS tracks into "folders", but not changing the real directory structure (unless user selects such option and the mode is not read-only). So that grouping is to be stored fully in the DB and fetched efficiently (like for displaying the "folders" only their IDs and names and metadata is to be fetched, not all images for each album, before we open it). Albums should allow nesting, and also this feature should allow putting single photo in multiple albums and subalbums, so it's like many-to-many relation. 

Map plugin should base on OpenLayers and by default use local OSM tile server (in default config it should be packed with the main app and start accordingly), all multimedia is to be efficiently prepared into clusters at resolutions, so "far away" from map I'd see a lot of clusters with photo counts, and when zooming, individual photos are to be displayed. However, optimize for displaying, since the total multimedia count might exceed hundreds of millions in the extreme cases (general is 100K-10M). GPS tracks are also to be rendered (when enabled and only which are enabled) and optimized for different resolutions, might be not the most precise at main view. There should be filters for time taken and for type (separate for multimedia and GPS tracks). To implement these features efficiently and deal with such large amounts of data, a great effort is to be put into DB schema design, field types, keys and indexing. Also the reverse geocode parsing (fetching location names based on geotags) has to be implemented with this plugin, and be disablable. Some of my phones didn't put geotags for videos, only for photos. For such files, a pin of other color/shape has to be put with guessed location (based on available GPS tracks for that datetime, or by weighted averaging nearest files having real geotags). I also want "live track" view for video: search a matching GPS track for video (same datetime span), and follow the marker on the map (at the map view at the bottom, or right half of the page) when video plays, synchronously. Like if you found track spanning from t0 to t1, and videos spans from t2 to t3 and [t0,t1] overlaps with [t2,t3] - when video is played at the intersection, marker should follow on the map, maybe not smoothly, but like update once per second, or smoothly if possible.


GPS tracks manager plugin is also a collection of tracks and a map view. It is used to store/join/separate/group them. Also an important feature is to "fetch all multimedia for the selected tracks", when selected tracks are shown in fine details on a map and then only photos that fall into their time stretch are displayed on map: with one color for photos that have GPS tags on them. Keep in mind, that due to some weird date/time issues, sometimes GPS datetime in EXIF is different from the file date and also different from GPS track's datetime, all these issues and offsets are to be found and also allow to shift locations of photos when bound to GPS tracks by given amount of seconds/minutes/hours. Because at some years my phone's time was 20 minutes off, at some point up to 97 minutes off real. But GPS, obviously, receives date and time from satellites. 

Video transcoding manager has to be a killer-feature visualizing ffmpeg and allowing to create custom presets. In some way it has to be like Handbrake WebUI. However, it should also allow autodetection of available codecs and hw accelerators (if machine has AMD, Intel or Nvidia GPU with hardware codecs), also pack full latest build of ffmpeg+ffmpeg_tools at its backend, and transcoding quality analyzers like VMAF. Its interface should allow selecting regular presets, or create your own, and script how presets are selected automatically when multiple files are chosen (like depending on resolution, framerate, bitrate, source container/codec, etc). Basic WebUI must be simple and intuitive whereas an advanced UI should be like rocket ship cockpit with a "Web GUI for ffmpeg" like StaxRIP, and allow good scripting (IDK processed at frontend side or at backend via some Lua bindings?). Queue has to be implemented, and of course kept on the backend side.

Base AI features manager has to manage available AI accelerators (like Nvidia/AMD ROCm/Intel IPEX GPUs, or CPUs – separate case for AVX512 supporting, only AVX2 supporting, older ones with SSE2 maximum) and probably communicate with sub-apps (I think pytorch container for each GPU type has to be a separate container). Basic AI features have to be face detection, image classification with some simple network. So that I could browse image by categories, or find all images with face of my best friend, or my parents. And a possibility to name these found faces, and merge/split them.

AI classification plugin is very important for the app to be must-have for transport fans. It should allow creating multiple DAG hierarchies (like country→railway operator→photos, and separate vehicle type → vehicle model → vehicle number) and select photos to train or finetune already trained models, with some basic (and optionally advanced) classifier configuration, by default some simple CNNs are to be used, so their training could be done even on CPU, or GPU with 4GB VRAM. And another mode to select photos and run classification over them, adding them tags, like "class predicted by <model> <train/finetune-aware version>".

Also here are some general app-wide ideas. Selection should allow multiple ways to select (like individual files in "explorer", or select folders, or select albums, or groups by other principle, like along GPS track, or with given AI class). Frontend must be correct and modern-looking reactive using Vue3 and TypeScript for all relevant scripts. WebUI must be slick and be very user-friendly, show progress indicators wherever possible, log all errors and details also to console log view. However, app-wide state has to be saved on backend (like all queues, parameters, jobs, etc), so that user could easily close the tab and nothing would stop/disappear. Also I'd like some session state token or something like that to be saved in browser, so that when user closes the tab and then opens new tab with the app page, it automatically shows the same view when users has closed it. For photo viewing/video streaming I would like it not require "sidecar generation" by default (optionally - yes, but with decent CPU/iGPU/GPU nowadays it just eats up a lot of space), so that when I open photo album - its draft previews are created on the fly, and video is either streamed as an original file over the LAN/network, or (selected by user, if admin allows that for group of files and group of users) transcoded by GPU/iGPU on-the-fly to some other format, like H264 or AV1 with lower bitrate (configurable at that options box for viewing, and not statically at app start).
An app must be able to work (be operational) fully autonomously, when there is no Internet connection, utilizing the data it already cached (like OSM maps on local server in Docker Compose service), all resources like fonts must also be present on the service host. It must even be able to launch in case it is introduced to a computer with Docker Compose or other available environment and then launchedm with no internet access at that machine at all. Everything must be self-sufficient and self-sustained. Of couse, some features like reverse-geotagging could be not fetching new data, but that's ok. Also, would be great to pack some general coarse map with countries and regions into the app itself, so at least it could decode them even if it never had an Internet access. And yeah, while Docker Compose seems to me like a good orchestration way, app must be runnable even without Docker Compose or Docker available, just natively on the machine, with addresses to other services specified, or possibly even without some of the services. So generally only the app distribution and PostgreSQL is a minimum requirement, without other dependencies just some plugins might be limited in functionality or not work, but no fatal errors preventing other features from working!
